## 1. 设计缘由

> 本节写成可直接发布的行文，不含内部路径与代码细节，供个人网站或对外说明直接引用。

### 1.1 为什么要重做色系统

这套色系统的起点不是"好看"，是三个被实算出来的问题。

**问题一：次要文字在三端里普遍不可读。** 按 WCAG 2.1 相对亮度公式逐条复算，Web 端四个主题的辅助色（`--mut`，用于日期、来源、序号）实测为：

| 主题 | 色值 | 对底对比度 | 要求 |
|---|---|---|---|
| 默认浅色 | `#8a93a4` | 2.88 : 1 | ≥ 4.5 ❌ |
| 阅读 | `#968a76` | 3.01 : 1 | ❌ |
| 护眼 | `#7f8f80` | 2.89 : 1 | ❌ |
| 深色 | `#6b7889` | 3.88 : 1 | ❌ |

本地审核后台更差：三个状态徽标（白字压底）是 3.19 / 3.09 / **1.66** : 1——1.66 那一档基本看不见。

**问题二：后台一直锚在错的基准上。** 后台是唯一使用第三方设计系统（Tabler）的一端，其内联样式硬编码的是 Web `:root` 的冷蓝色值；而 Web 实际默认渲染的是暖纸主题。也就是说，后台的视觉基准从来不是"用户看到的 Web"。三端里只有鸿蒙端是真正设计过的。

**问题三：所谓"已对齐"只做了一半。** 此前一轮把 Web 向鸿蒙靠，但只改了 `reading` 一个主题的高亮色；其余三个主题仍是旧值，切换主题即穿帮。主色本身也存在两个值并存（`#4a7355` 与 `#4C795B`），文件里却写着"与原生端一致"。

结论：缺的不是"统一"，是**一套被验证过的基准**。

### 1.2 为什么主色是靛

品牌色相的选择用**色相环求解**，不是凭手感。约束是：产品已有的语义色与标注色占据了环上的多个区间，品牌色落进去就会被误读。

| 候选 | 色相 | 最近邻 | 距离 | 判定 |
|---|---|---|---|---|
| 墨青 | 176° | 成功绿 156° | **19.8°** | ✗ 品牌按钮会被读成"成功态" |
| 绛 | 355° | 危险红 2° | **6.7°** | ✗ 品牌按钮会被读成"危险操作" |
| 深赭 | 28° | 强调琥珀 35° | **6.9°** | ✗ 与强调色撞 |
| **靛青** | **230°** | 术语青 191° | **38.9°** | ✓ 环上空档最大 |

靛青成立的另一个理由是**语义**，不只是"没冲突"：中国传统色里的「青衿」正是学子之色（《诗经》"青青子衿"）——而这款产品的用户就是青衿。宣纸暖底配靛墨是书卷的经典搭配；靛与朱批的红构成传统**朱墨对比**，而产品的核心动作恰恰是"给原文划考点"。

### 1.3 为什么中性色是"暖墨"而不是冷灰

原鸿蒙端的辅助色 `#6A7280` 在白卡上达 4.85 : 1，但在暖米底上只有 4.30 : 1，不达 AA——其文档已如实登记"仅限白卡内使用"。

新中性阶改为**暖墨**（色相 34–37°，低饱和）：辅助色 `#635E56` 在暖底 5.70、纸卡 6.32，**双底都过 AA**。也就是说新色阶不只是"更统一"，它比现状**更好**。

### 1.4 为什么深色不做反色

暖米底 `#F5F1E8` 直接取反会得到脏灰，暖调尽失；纯黑底配暖色文本夜间反光过强。所以深色是**另一套独立取值的"深暖灰"体系**，文字用暖白 `#EDE8DE` 而非纯白——纯白在暗底上会有眩光拖影。

深色下的标注底色同样需要重新取，不能沿用浅色的浅底（浅底在暗环境会眩光）。本轮实测发现一个隐蔽缺陷：最初深色标注底与深色卡片面的**可见度只有 1.16–1.51 : 1**，文字对比度虽然合格（8.6–11.2 : 1），但"标记本身看不见"。重新取值后可见度提到 1.65–1.80 : 1，同时文字对比度仍保持 ≥ 7.2 : 1。

### 1.5 为什么统一到 token 而不是统一到组件

后台是**操作效率优先**的表格密集型界面，Web 端是阅读流，手机端是单手可达的卡片流——三者的组件形态本来就该不同。强行统一组件，等于用一致性换掉每一端的长处。

所以统一的是**值**（颜色、字号、行高、间距、圆角、时长、缓动、阴影、触控尺寸），各自保留**形态**。成立的判据很直接：三端渲染同一套 token 值之后，差异应当只剩组件形态与信息密度，**不应剩任何颜色**。

## 4. 三端 token 映射

规范键用点分命名（`group.sub`）。三端各自落地方式：

| 规范键 | CSS 变量 | ArkTS | 后台 |
|---|---|---|---|
| `color.ink` | `--color-ink` | `KColor.ink()` | `--kg-ink` |
| `color.brand` | `--color-brand` | `KColor.brand()` | `--kg-brand` |
| `space.m` | `--space-m` | `KSpace.m()` | `--kg-space-m` |
| `radius.lg` | `--radius-lg` | `KRadius.lg()` | `--kg-radius-lg` |
| `font.body` | `--font-body` | `KFont.body()` | `--kg-font-body` |
| `line.reading` | `--line-reading` | `KLine.reading()` | `--kg-line-reading` |
| `dur.md` | `--dur-md` | `KDur.md()` | `--kg-dur-md` |
| `shadow.card` | `--shadow-card` | `KShadow.card()` | `--kg-shadow-card` |
| `size.touchMin` | `--size-touch-min` | `KSize.touchMin()` | `--kg-size-touch-min` |

后台额外**覆盖 Tabler 变量**，使既有类名自动换肤、布局零改动：

```css
:root{
  --tblr-primary:      var(--kg-brand);
  --tblr-body-color:   var(--kg-ink);
  --tblr-muted:        var(--kg-mut);
  --tblr-border-color: var(--kg-line);
  --tblr-bg-surface:   var(--kg-surface);
  --tblr-light:        var(--kg-surface-alt);
  --tblr-danger:       var(--kg-danger);
  --tblr-success:      var(--kg-success);
  --tblr-warning:      var(--kg-warning);
}
```

### 4.1 承载方式（单一数值源）

```
packages/design-tokens/tokens.json        ← 唯一数值源
        ├─ generate.mjs  → apps/web/src/styles/tokens.generated.css
        │                → pipeline/src/kaogong/review/ui/tokens.css
        └─ scripts/audit-tokens.py  （纯 Python，CI 用，无 Node 依赖）
              ├ sha256 比对：源 ↔ manifest ↔ 产物（改了源没重跑生成器即失败）
              ├ 提取 apps/harmony/.../Tokens.ets 的色值与 tokens.json 逐项比对
              ├ WCAG 断言（文本 4.5 / 非文本 3.0）
              ├ 色相环间距断言（品牌 vs 语义/标注 ≥ 30°）← 本次踩过的坑，固化成检查
              └ 裸 hex 扫描（三端消费文件）
```

**两个关键取舍**：

1. **鸿蒙 `Tokens.ets` 保持手写，只受审计约束，不做生成覆盖。** 该文件承载不可再生的踩坑注释（`fontScale` 的 ArkUI 依赖追踪陷阱、`MUT` 仅限白卡、"深色不做反色"的理由）。生成器覆盖会毁掉这些知识。**值**由审计强制对齐，**结构**留给人维护。
2. **生成器只负责 CSS**（确定性、机械性产物）。ArkTS 是结构性代码，且禁索引签名，全量生成可读性差且难人工扩展。

后台接入用 FastAPI 现成先例（`server.py` 已有 `@app.get("/fonts/uploads/{filename}")` 返回 `FileResponse`）：

```python
@app.get("/review/tokens.css")
def review_tokens_css() -> FileResponse:
    return FileResponse(UI_DIR / "tokens.css", media_type="text/css")
```

`ui/index.html` 里的 `<link>` **必须置于 Tabler CDN `<link>` 之后**。

## 5. 主题集合

**收敛为 light + dark 两套**，三端一致。

- `light`：暖纸底（原 Web `reading` + 原鸿蒙浅色合并为同一个 light）
- `dark`：深暖灰（非反色）

**退役**：Web 的 `:root` 冷蓝 light、`green` 护眼豆沙绿、冷色 `dark` 三套。

理由：`light` 的暖纸底本身就是护眼方案；"护眼绿"作为独立主题带来的是四套 token 的维护成本，而非用户价值。若要保留"底色可选"，降级为 `light` 内的 `paper` 变体（只换底色 token），不进主题系统。

配套：Web 的「主题」按钮改为「深浅切换」——现状是四档循环，用户需点三次才回到原主题。

| **次按钮** | 高 40，`radius.full`，`surface` 底 + `line` 描边 + `brand` 字 |
| **列表行** | 整行可点，最小高 **44**；选中态 `brand` 底 + 白字 |

### 无障碍硬指标

- 交互元素高度 **≥ 44**（vp / px）
- 文本对比度 **≥ 4.5 : 1**（大字号 ≥ 3 : 1）
- **不依赖颜色单独传达信息**：标注除底色外同时有类型文字标签
- 尊重 `prefers-reduced-motion`

## 10. 附录 · 彩蛋规格：色相环实验台（2026-09-12 定案，迁移完成后实施）

### 10.1 定位

把本文 §1.2「品牌色相用色相环求解」的过程**做成可玩的东西**。它的价值不在娱乐，在于让"为什么是 230°"变成任何人都能自己验证的结论——而不是一句设计者的断言。

### 10.2 入口

**在主站搜索框输入 `qingjin` 回车**，落到色系统展示页。

选这个触发方式的理由：

- **有语义**：青衿正是品牌色命名的由来，触发词本身就是答案的一部分。
- **三端一致**：搜索框三端都有，触摸与键盘都可达；不像键盘序列（如 Konami、输入 `INDIGO`）在手机端无法实现。
- **不误触**：`qingjin` 不是任何真实搜索词，不会污染正常检索。
- **实现代价低**：复用既有搜索页，不需要额外的全局事件监听。
- **符合惯例**：搜索无结果页放彩蛋是成熟做法，用户不会觉得突兀。

呈现方式：在「没有找到相关内容」的空态**下方**多出一行提示（例如「不过，这里藏了一个东西」），点击进入展示页。**默认不提示存在**——彩蛋被发现才有意义。

### 10.3 实验台行为

一个可拖动的色相滑块（0–360°），实时联动显示四项：

| 显示项 | 说明 |
|---|---|
| 品牌色 | 当前色相下的 brand 色值 |
| 全环最近距离 | 与全部语义色 / 标注色的最小色相距离；**< 30° 标红告警** |
| 对暖底对比度 | 当前 brand 对 `#F5F1E8`；**< 4.5 标红** |
| 对纸卡对比度 | 当前 brand 对 `#FFFDF6`；**< 4.5 标红** |

滑块默认停在 230°，结论行显示实际值：**「距最近语义色 38.9° · 暖底 7.70 · 纸卡 8.53 —— 两项硬约束均通过」**。

用户拖动时会**亲眼看到**滑进 176° 就撞上成功绿、滑进 355° 就撞上危险红、对比度也会掉破 4.5——这就是把 §1.2 那张否决表变成交互。

### 10.4 工程约束（实施时必读）

1. **静态生成，零后端**。展示页走既有 `output: "static"`，不引入服务端计算。
2. **⚠️ 对比度公式存在双实现风险**。实验台在浏览器用 JS 算，`scripts/audit-tokens.py` 在 Python 算——两套实现一旦漂移，就会出现"网页显示 7.70、脚本说 7.68"这种最难查的不一致。
   **对策**：在 `packages/design-tokens/` 下维护一份**测试向量**（若干色对 + 期望比值），JS 与 Python 两侧各跑一遍并断言一致；该断言进 CI，两侧任一改动即失败。
3. **色值来源是 `packages/design-tokens/tokens.json`**，不硬编码在页面里。
4. **约束阈值（≥30°、≥4.5）同样进测试向量**，两边共用，不各写一份魔数。
5. §1「设计缘由」的成文段落直接作为展示页的正文——**同一份文案，不在页面里重写一遍**（避免两处维护）。

### 10.5 与个人网站的关系

同一份展示页（含缘由正文 + 色卡 + 实验台）应当能**独立发布**到个人网站。因此实施时保持：不依赖主站的登录态、导航、API，可整页拷贝或作为独立路由导出。
