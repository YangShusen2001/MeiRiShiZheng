# ADR 0010：设计令牌单一数值源与生成式 CSS

- **状态**：已接受（第 0–3 步完成；第 4 步深色按用户指示留到最后）
- **日期**：2026-09-12
- **依据**：`docs/design/design-system-v3.md` §4.1（该文是令牌的值与理由的唯一来源，本 ADR 只记录**架构取舍**）

## 背景

三端（本地审核后台 / Web / 鸿蒙）此前各有一套颜色与字号，且后台的视觉基准是错的——它是唯一使用第三方设计系统（Tabler）的一端，内联样式里硬编码的是 Web `:root` 的冷蓝值，而 Web 实际默认渲染的是暖纸主题。三端之间没有共同事实源，任何一次改色都要人工同步三处，且已实测出主色 `#4a7355` 与 `#4C795B` 并存、Web 高亮色只在 `reading` 一个主题对齐等漂移。

## 决策

- 新建 `packages/design-tokens/`，`tokens.json` 是**唯一数值源**；颜色、字号、行高、间距、圆角、动效、阴影、触控尺寸全部在此声明。
- `generate.mjs` 由源生成**两份 CSS**：`apps/web/src/styles/tokens.generated.css`（Web，`:root` 浅色 + `[data-theme="dark"]` 深色）与 `pipeline/src/kaogong/review/ui/tokens.css`（后台，`--kg-*` + 覆盖 9 个 `--tblr-*`）。产物带 `SOURCE_SHA256` 指纹注释，且**入库**——否则无法检出「改了源没重跑生成器」。
- **不生成 ArkTS**。鸿蒙 `Tokens.ets` 保持手写：它承载不可再生的踩坑注释（`fontScale` 的 ArkUI 依赖追踪陷阱、`MUT` 仅限白卡、"深色不做反色"的理由），生成器覆盖会毁掉这些知识。**值由审计强制对齐，结构留给人维护。**
- `scripts/audit-tokens.py`（**纯 Python、无 Node 依赖**）作为 CI 门禁，硬性检查：源指纹一致、测试向量、WCAG 成对断言、品牌色相环间距 ≥30°、后台接线（9 个 Tabler 覆盖键 + link 位于 Tabler 之后）。
- `packages/design-tokens/test-vectors.json` 是**对比度公式双实现的共用契约**：浏览器侧（`wcag.mjs`）与 Python 侧（`audit-tokens.py`）各跑同一组向量，期望值取自规范正文里的实算记录（独立于实现，不由实现反推）。含 7 条**负例**（v3 之前线上的真实值），用于证明门禁不是空转。
- 审计的**迁移债务项**（裸 hex 计数、鸿蒙值漂移）默认只告警，`--strict` 才升级为失败。理由：这两项要等第 2、3 步才可能清零，若一开始就硬失败，等于用一个还没做的目标把仓库卡死；但债务必须出现在结果里、可被测试断言，不能静默。
- 后台 Tabler 由 `@latest` 改为锁 `1.5.1`（规范 §7 债务 2），`dist/css/tabler.min.css` 已确认为该版本的声明式 CSS 入口。

## 后果

后台与 Web 从此**锚在同一个数值源上**：改 `tokens.json` → 重跑生成器 → 刷新即换肤。
后台三个状态徽标的最低对比度从 1.66:1 提到 6.3:1 以上；Web 的 97 处裸 hex 清零。

**Web 侧的一个额外取舍**：没有把 1300 多行里的 `var(--bg)` 等旧变量名全量改名，而是在 `global.css`
顶部加了一层「旧名 → 令牌」的**别名层**，只把值的来源换成单一事实源。理由是最小切口：
全量改名的风险与评审成本远高于收益，而别名层已经拿到了「单一事实源」这个真正想要的东西。
将来若要正名，可以逐页替换后删掉别名层。

未完成、需后续处理：

1. **Web 的标尺还没归并**：字号仍散落 13/15/16/18/22/30/38px（规范 §3.1 要求就近并入 8 档），
   阅读正文行高仍是 1.9（规范 §3.2 要求 1.8，且**自注「需两端视觉确认」**）。
   这两项都会肉眼可见地改变版面，**必须由人看过再动**，故未执行。
2. **深色排到最后**（用户 2026-09-12 拍板）。深色令牌已随生成器产出且经无头渲染验证可用，
   但目前**不对用户开启**：Web 固定浅色、主题按钮下线。开启只需恢复 `Base.astro` 里的
   `matchMedia` 分支与按钮，样式零改动。
3. **鸿蒙值漂移 23/36 项**（第 3 步）。`Tokens.ets` 仍是旧深绿体系；收口需人工在 DevEco 点 Run 真机确认。
4. **后台仅浅色**。未生成深色令牌块——后台是本地工具、Tabler 默认不跟随系统深色。
5. **Vendored Tabler 未决定**。锁 `1.5.1` 已解决「CDN 推新版即变」，离线场景仍未覆盖。
6. 规范正文中「深色主按钮 = brand 底 + ink 字」的 `ink` 指代不明；实测 `#EDE8DE` 压 `#9099E0` 仅 2.20，
   故取 `brandDeep #232C5C`（4.93，已进向量）。规范正文待同步这一取值。
7. **软底与浮层阴影用 `color-mix()` 派生**（如失败行底色 = 危险色 8% 混卡片面），
   而不是新增令牌。代价：浏览器下限抬到 Chrome/Edge 111+ / Safari 16.2+ / Firefox 113+。
   选择派生的理由是「不写死、不新增未经评审的色值」，若将来要支持更老的浏览器，需改为令牌。

### 另一个必须记录的仓库风险：画布宿主会改写 HTML 源文件

实测：`pipeline/src/kaogong/review/ui/index.html` 在 HEAD 里 0 处 `data-page-node-id`，
经一次编辑后涨到 120+ 处，`git diff` 从 2 行变成 208 行；`git checkout --` 还原后**毫秒级又被写入**
（injected id 每次都不同）。`docs/design/color-system-v3.html` 与 `_review/*.html` 也中招，
其中 `_review/label.html` 的注入**已经进了 HEAD**。

后果是评审困难 + 宿主产物混入库。对策：`scripts/strip-canvas-injection.py`（检查模式可作提交前门禁）。
**提交前先跑 `python scripts/strip-canvas-injection.py`，有输出就先清。**
