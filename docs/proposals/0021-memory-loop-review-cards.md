# 0021 记忆闭环 MVP：考点卡片 + 间隔重复 + 主动回忆自测

- 状态：**已实施**（2026-08-20，TASK-0021 完成，见 docs/tasks/0021-memory-loop-review-cards.md）
- 日期：2026-08-20
- 关联：0020（性能）、0013（审核 Agent）、`docs/product/product-overview.md`（产品定位）
- 触发：产品现阶段"给得多、留不住"——每天聚合大量时政，但考生刷完即忘，"真正熟悉并记住考点"这一最终目标没有任何机制支撑。经多轮调研确认：记忆靠**间隔重复 + 主动回忆（自测）**，而非重复阅读。本提案引入最小可行闭环验证这一核心假设。

---

## 1. 背景与目标

### 1.1 要解决的问题

| 现状 | 问题 |
| --- | --- |
| 每日聚合 + AI 标注 + 精读 | 只"呈现"，无"记忆"环节 |
| 已有「每日一练」（选择题） | 定位是"日测"，按天一次性，不跨天复现 |

**目标**：让考生对"必记考点"形成长期记忆。MVP 只验证一件事——**"翻卡自测 → 4 档自评 → 间隔重复调度"这个闭环能否跑通**，不做选择题、不做 AI 举例、不做激励系统。

### 1.2 记忆科学依据（结论，不展开）

- **检索练习（testing effect）**：主动回忆比重读/划重点的记忆效果强一个量级。
- **间隔重复（spaced repetition）**：按遗忘曲线自适应调度复习，算法用 **FSRS**（Anki 下一代调度器，学界/工业界事实标准）。
- 技术实现：**[ts-fsrs](https://github.com/open-spaced-repetition/ts-fsrs)**（FSRS 官方 TS 实现，纯函数库，ESM 可跑在 Cloudflare Workers）。

## 2. 与现有「每日一练」的边界（避免混淆）

| 维度 | 每日一练（现有） | 考点卡片（新增） |
| --- | --- | --- |
| 题型 | 选择题（4 选 1） | 问答翻转（一问一答） |
| 时间 | 按日期，当天一次性 | 跨天，间隔重复 |
| 目的 | 检验"今天文章"的掌握 | 长期记住"必记考点" |
| 数据 | `practice` + `wrongQuestions` | 新表 `reviewCards` |
| 内容源 | 每日文章生成 | 策展人手工提炼的原子考点 |

两者**并行、互补、互不改动**。MVP 只新增卡片闭环，不碰每日一练。

## 3. 方案设计

### 3.1 数据模型（两处，严格分层）

**A. 卡片内容 = 静态策展内容，进 `content/cards/`（只读，同 AI 标注一样不分用户）**

```json
// content/cards/15w-plan.json
{
  "policy": "十五五规划建议",
  "cards": [
    {
      "id": "15w-loc-001",
      "question": "「十五五」时期的官方定位是什么？",
      "answer": "基本实现社会主义现代化「夯实基础、全面发力」的关键时期，具有承前启后的重要地位。",
      "tags": ["定位", "关键时期"]
    }
  ]
}
```

- 配套 `content/schema/card.schema.json` 做 JSON Schema 校验（与现有 content 产物一致）。
- 每张卡：**原子**（一问一答）、**硬考点**（官方明确定位/原则/目标，非开放论述）。

**B. 复习状态 = 用户数据，进 D1 新表 `reviewCards`（apps/api 唯一入口）**

```ts
reviewCards:
  ownerId      text   // "user:<id>" | "device:<id>"，复用现有身份域前缀
  cardId       text   // 对应 content/cards 里的 id
  fsrsState    text   // ts-fsrs 的 card state 序列化（JSON）
  dueAt        integer // 下次到期时间（unix 毫秒）
  reviewCount  integer // 已复习次数
  lastReviewAt integer // 最近一次复习时间
  // 复合主键 (ownerId, cardId)
```

### 3.2 架构边界（守 AGENTS.md 红线）

| 内容 | 位置 | 说明 |
| --- | --- | --- |
| 卡片题目/答案 | `content/cards/` → apps/web 构建时读 | 静态只读内容，不分用户 |
| FSRS 调度 | apps/api（ts-fsrs 纯函数，服务端算） | 防止调度被篡改，且状态一致 |
| 复习状态 | D1（apps/api 独有） | 用户数据唯一入口 |
| 复习 UI | apps/web | 不直接访问 D1 |

**关键**：卡片内容（策展产出）与复习状态（用户行为）彻底分离——与现有"AI 标注只读 / 用户标注进 D1"的分层完全同构，不破坏任何模块边界。

### 3.3 交互设计（已与用户确认）

- **入口**：顶部/侧栏「今日待复习」，每日任务形态（非题库浏览）。
- **闸门**：软闸门——打开站检测到今日到期卡片时，弹出**毛玻璃遮罩 + 居中卡片层**盖住今日内容；卡片层底部有不起眼的「今日跳过」，不锁死用户。
- **翻卡**：先显示问题 → 点击翻面看答案（主动回忆）→ 底部 4 档自评。
- **4 档自评 → FSRS rating**：忘了=Again(1)、模糊=Hard(2)、会了=Good(3)、轻松=Easy(4)。
- **完成**：今日到期卡全部评完 → 遮罩收起露出内容，显示打卡完成态。
- **移动端**：全屏卡片（屏幕小，遮罩无意义）。
- **跳过记忆**：MVP 用 localStorage 记"今日已跳过"（纯前端，不进 D1）。

### 3.4 契约（packages/contracts）

- `content.ts` 新增卡片内容类型（`ReviewCard`、`CardDeck`）。
- `api.ts` 新增：

```ts
// GET /api/review/due 响应：到期卡片 id 列表（内容由前端本地取）
reviewDueResponseSchema = { dueIds: z.string[] }

// POST /api/review/grade 请求：提交一张卡的自评
reviewGradeSchema = {
  cardId: z.string(),
  rating: z.enum(["again","hard","good","easy"]), // → ts-fsrs Grade 1..4
}
// 响应：这张卡的下次到期时间
reviewGradeResponseSchema = { dueAt: z.number(), reviewCount: z.number() }
```

### 3.5 API 设计（apps/api，新增 `routes/review.ts`）

| 路由 | 作用 | 数据流 |
| --- | --- | --- |
| `GET /api/review/due` | 返回今日到期 card_id 列表 | 查 D1 `dueAt <= now`；**新卡**（无记录）按文件内顺序补足，每日新卡上限 **5 张** |
| `POST /api/review/grade` | 提交自评，用 ts-fsrs 算下次 due | 读 D1 fsrsState → ts-fsrs `next()` → 写回 D1 |

- 内容（题目/答案）**不经过 api**，前端用 `dueIds` 从构建产物里查卡片内容。
- 身份：复用 `resolveOwnerId`（登录用户 + 匿名设备均可用）。

## 5. 风险与边界

1. **ts-fsrs 需验证在 Cloudflare Workers 运行时无 Node 依赖**（预期纯函数可跑；若遇兼容问题，降级为自实现简化 FSRS 表或把调度移到前端，但优先保持服务端算）。
2. **新卡引入节奏**：每日新卡上限 **5 张 + 到期卡**（用户已确认），新卡按文件内顺序引入，避免一次性 30 张砸出。
3. **卡片内容与"精读"的关系**：MVP 卡片独立于精读页（先跑通闭环）；后续"卡片 ↔ 精读"锚定在阶段 2 做（接 🥈 结构化考点库）。
4. **FSRS 参数**：先用 ts-fsrs 默认参数（已针对大规模用户优化）；不做个性化调参。
5. **不新增基础设施**：D1 加一张表 + apps/api 加一个路由 + 一个 npm 依赖，无新服务，符合"不引入微服务/基础设施"红线。
