## 1. TL;DR

1. **项目卡在"内核没有产品化"，而不是"功能不够"。** 定位是「时政考点记忆系统」，但生产内容仍是信息流：7 个内容日产出 215 篇（08-19 单日 63 篇），而 `aiCards` 只出现在 5 篇、跨日卡片池分发产物 `apps/web/public/content/cards.json` 只有 **54 张**（30 人工 + 24 文章卡）。**记忆闭环的输入端几近枯竭，且约 10–11 天会耗尽。**
2. **找到 P0 根因**：`curation.py:101` 的 prompt 示例 id（`15w-plan`）与真实主线 id（`fifteen-five-plan`）不一致，`:165` 又是精确匹配 → **主线归属线上 ~0% 命中 → picks 只跑一半**。这是"减量没做成"的技术原因（详见 §2.5）。
3. **单点阻塞是"内容管道产能"，不是任何端功能。** 卡池 54 张（分发层已合并）约 10–11 天会枯竭，决定了端侧功能在服务一个**会静默失效**的数据源；Web/App 谁先谁后、首页怎么改，都受它约束。
4. **下一步唯一正确的起点：先修 P0（≤2 天）→ 把管道跑成"每日 2–5 篇 + 每篇必出卡"，并让 `picks.json` 每天产出。** 端侧唯一例外是 App 首页改版（减项、不白屏），**可与迭代 1 并行**，但要求 1.1/1.2 在 10 天内落地。
5. **测试全绿 ≠ 功能可用**：194 个测试通过，但没有一个用真实 `_grade_messages()` 输出喂校验函数，bug 长在"接缝处"、潜伏至今（见 §2.5）。
6. **自诊断文档的方向正确（§7.5 的自我校准尤其诚实），但内部有 4 处需要修正**：卡池被低估、"做减法"与"做转化"的顺序不可互换、"App 唯一主力"在构建卡点未解前代价被低估、"先做透广东"缺少数据支撑。详见 §3。
7. **两个 release blocker 的正确处置：`REL-PRODUCTION-DEPLOYMENT` 补证据即可关闭（生产实测可用，是账没记）；`REL-NEWSLETTER-PROVIDER` 应降级/移出 release 门禁**——订阅邮件不在当前产品定义的关键路径上，用 high 阻塞发布是拿次要功能卡住主干。

## 2.5 P0 根因：prompt 里的 id 口径矛盾，导致「主线归属」线上 0% 命中

这是本次评审最重要的技术发现，也是"picks 只跑了一半"的直接原因。

**证据链（`pipeline/src/kaogong/curation.py`）：**

| 位置 | 内容 | 问题 |
|---|---|---|
| L87 | `line_list = "、".join(f"{p['id']}({p['name']})" ...)` | 清单里发的是**真实 id**，如 `fifteen-five-plan` |
| **L101** | `"输出形状：{...\"policyLine\":\"15w-plan\"...}"` | 示例里发的是**短 id `15w-plan`** |
| L98 | "policyLine 从给出的主线 id 中选" | 指令与实际示例**自相矛盾** |
| **L164-165** | `line_id = line if any(p.get("id") == line for p in lines) else None` | **精确字符串匹配**，不归一化 |
| L101 vs `content/policy-lines.json` | 实际 id 是 `fifteen-five-plan` / `govt-work-report-2026` | `15w-plan` **根本不存在** |

**后果**：模型看到示例用了短 id，输出 `15w-plan`（而非 `fifteen-five-plan`）→ L165 精确匹配失败 → `policyLine` 全部归 `None` → **所有文章都无主线归属** → `assign_slots` 的 essay/exam/extra 依赖主线分流，于是槽位大面积塌陷 → picks 只选出极少数文章（4/7 天有 picks，且内容稀少）。

**这与 §2 的"215 篇 vs 端上 54 张卡"是同一根因的两端**：减量（picks）没做成的技术原因，就在 L101 这一行示例 id 上。

### 为什么这个 bug 能潜伏至今：测试全绿 ≠ 功能可用

**`pipeline/tests/test_curation.py` 共 20 个测试文件，全部通过；但没有一个测试用真实 `_grade_messages()` 的输出喂给校验函数。**

| 测试 | 位置 | 喂的输入 | 为什么测不出来 |
|---|---|---|---|
| `test_assign_slots_structure` | L66-86 | `call=_call([...])` → **手写的、格式完全正确的** `"policyLine": "fifteen-five-plan"` | prompt 里的 id 矛盾**永远不会被触发**；测的是"给定正确输入，槽位逻辑对不对"，而线上坏的是"输入永远不正确" |
| `test_assign_grades_uses_model_and_validates_line` | L50-58 | stub 返回 `"fifteen-five-plan"`，并断言非法 id `"不存在的线"` → `None` | L58 **专门断言了"非法 id 归 None"是被认可的行为**——但没人发现**真实 prompt 下所有 id 都是"非法"的** |
| `test_curate_content_end_to_end` | L98-137 | L128 stub 返回 `"policyLine": "fifteen-five-plan"`，L134 断言 `saved["policyLine"] == "fifteen-five-plan"` ✅ | **集成测试也全绿，线上 0% 命中** |
| 真实调用路径 | L143-145 `call(...)` | 测试里**全部被 stub** | 没有任何测试校验"真实 prompt 产出的 id 形态" |

> **一句话可引用**：194 个测试全绿，因为**没有一个测试是用真实 `_grade_messages()` 的输出喂给校验函数的**。测试覆盖了"下游逻辑正确性"，完全没覆盖"上游契约一致性"——**而 bug 恰好长在接缝处**。

### 这条 P0 是什么时候坏的（08-17 唯一命中，此后归零）

逐日统计 4 个 `picks.json` 的 `assignments` 命中 `policyLine` 的情况：

```
2026-08-17: assignments  4 条, 命中 policyLine 的 1 条  → ['f80313d7b2' → 'fifteen-five-plan']
2026-08-19: assignments 59 条, 命中 policyLine 的 0 条
2026-08-20: assignments 54 条, 命中 policyLine 的 0 条
2026-08-21: assignments 45 条, 命中 policyLine 的 0 条
```

**这条线索把根因从"一直坏"升级为"何时坏的"，对修复方案有直接指导价值：**

1. **08-17 命中过 1 条** → `policyLine` 匹配链路**本身是通的**，不是从来没工作过。
2. 正因为 08-17 命中了，它的 picks 才写出 `headline: 'f80313d7b2'` 且该篇**有 `aiCards`（4 张）**；而 `f80313d7b2` 也成了 08-19/08-20 的 `supplement` 补剧来源——**一条命中撑起了后续三天的"凑数"**。
3. **08-19 起断崖式归零** → 更像**回归（regression）**，而非"设计缺陷从未生效"。修复方向因此应加一步：**查 08-17 之后 `curation.py` / `card_ai.py` / prompt 是否有改动**（`git log -p --follow pipeline/src/kaogong/curation.py`），确认是"prompt 被改坏了"还是"主线池/数据变了导致模型不再输出合法 id"。若确认是回归，修复成本更低（可能只需 revert 一处），且**必须补回归测试锁住**。
4. **另一种解释同样成立**：08-17 的 `assignments` 只有 4 条（当天也只有 4 篇文章），而 08-19 起是 59/54/45 条 → **08-17 是"手写策展的小样本日"，08-19 起才是管道全量跑的第一天**。即：**08-17 的内容可能是人工策写的（或用了不同的 prompt/主线），管道从未在真实规模下成功过**。

> **定性小结**
> - **已知**：08-17 命中 1 条，此后 3 天（08-19/20/21）命中 0 条，且三槽位全空。
> - **定性结论（已用 git 历史确证）：自诞生即存在的结构性契约不匹配，非回归。**
>   短 id 来自提案设计值（`docs/proposals/0022-curation-memory-pivot.md:36`），长 id 是实施时改的，**prompt 示例照抄提案后未同步**；且 `curation.py` 与 `policy-lines.json` 同为 `8ba7a82`「保全既有未提交工作（非本次任务产出）」提交入库，**从无演进历史**（不存在"曾经好过"的窗口 → 排除回归）。
> - **08-17 唯一命中的解释**：当天 `assignments` 仅 4 条（`content/` 里唯一被 git 跟踪的"精选小样本策展日"），模型在 4 篇里偶然命中 1 篇；一旦进入 **46–59 篇的真实规模，few-shot 里的 `15w-plan` 就被照抄 → 必然全灭**。典型形态：**小样本偶然成功、真实规模必然失败**。
> - **修复不能只改示例字符串**（主线池改名会再次引入同类问题），必须走「**示例动态生成 + 校验归一化 + 三槽位全空判 degraded**」三道防线（技术方案见架构师文档）。
> - **"三槽位全空判 degraded"这条门禁无论根因何时生效都成立**——它守护的是"结果"，不依赖"何时坏的"（见 §6 / P7）。


`curation.py:432-439` 只在 `picked` 为空时不写文件（降级为 `picks_missing`）。但当 picks **非空却只有 1 篇、且三个槽位（essay/exam/extra）全空**时，它会**安静地写出一个"合法但错误"的文件**——因为 `picks.schema.json` 只要求 `minItems:1`。

这正是 `AGENTS.md` 第 8 条「内容源失败、条目异常减少或 Schema 校验失败时，流水线必须给出非成功质量状态」**未被执行的实例**：schema 过了，质量没验。

### 方法论教训（有普遍价值）

1. **"契约在接缝处断裂"的 bug，单元测试天然测不到**，必须靠**契约/集成测试**：用真实 prompt 构造 → 断言模型可能返回的各种 id 形态（长 id / 短 id / 名称 / 带引号 / 大小写差异）都能被归一化。
2. **更根本的防线是运行时可观测**：产出 `picks.json` 时，若 `essay`/`exam`/`extra` 三槽位**同时为空**，这本身就是**强异常信号**（设计上每天至少应有料）→ 应**直接判 degraded 并告警**，而不是静默发布。
3. **修复要点**：L101 示例 id 改为与真实 id 一致（或改为变量注入 `lines[0]['id']`）；L165 的匹配加**归一化**（去空格/引号、大小写、短 id 别名映射）。二者缺一不可——只改示例，模型仍可能输出变体；只加归一化，模型仍会被错误示例误导。

## 4. 真正的瓶颈排序（影响 × 成本）

| 顺位 | 瓶颈 | 影响 | 成本 | 是否单点阻塞 | 说明 |

## 5.1 回答用户点名的 5 个具体决策

### 决策 A：先提卡片率，还是先"AI 做减法"？顺序能否互换？

**结论：不能互换。必须先"做减法（每日 2–5 篇）"，再"做转化（每篇必出卡）"，且两者应同批发布。**

- **依据**：自诊断把"每日 2–5 篇"排第 1、"卡片率 100%"排第 2，是对的。因为若先提卡片率而不减量，等于对 **215 篇**都产卡——API 成本 ×10，且大量卡来自你根本不会让用户读的文章，是**无效库存**。
- **减法是转化的前置**：卡池的"有效规模" = 入选篇数 × 产卡率。先砍到 2–5 篇/天，产卡率的提升才花在刀刃上。
- **但两者不可拆成两个迭代**：只减量不产卡 → 卡池仍空；只产卡不减量 → 成本失控。**同批上线**（迭代 1.1 + 1.2）。
- **对自诊断的修正**：它把"AI 做减法（今日 2 篇 + 理由）"放在 **90 天第 8 项**，但把"每日 2–5 篇"放在 **30 天第 1 项**——**这两件是同一件事**。"砍到 2 篇"如果没有"为什么是这 2 篇"的理由，用户不信任；"给理由"如果没减量，纯属给信息流加注释。**应合并为 30 天的同一项，而不是跨越 60 天。**

### 决策 B：端侧首页改版会不会暴露空态？有这个风险该先做什么？

**结论：方向要反过来——首页已有复习区块且不会白屏，所以没有"空态翻车"风险。真正的隐患是"10–11 天后静默失效"。因此 2.1 可与迭代 1 并行，但约束改为：1.1/1.2 必须在 10 天内落地。**

- **首页"今日待复习"区块已存在，不是"要改才有"**（`apps/harmony/entry/src/main/ets/view/HomePage.ets`）：
  - `:49` 注释「今日待复习卡片数。让'必须回来'这件事在首页可见。」
  - `:443-497`「今日复习入口」：有待复习时主色底强调、文案 `今日待复习 ${this.dueCount} 张`；无待复习时降级为 `考点复习` + `查看`。
  - `:636` 注释「复习入口常驻：即使内容还在加载，它也该可见（它不依赖当日内容）」。
  → 所以迭代 2.1（首页改「今日素材 → 到期复习」）**实际是删掉长列表（减项），不是从零加区块（加项）**。我先前把它的成本与风险都高估了。
- **不会白屏**：`Review.ets:256 dueCards()` 是**本地算**到期（`:260` 遍历 `cards` + `progress`）；端上注释 `:87`「题库拉不到不算错误：首页仍有内容可看，复习入口显示为 0」、`:79`「待复习数量：卡片取自本地缓存，离线也能算出来」。最差显示 `考点复习 / 查看`。
- **真风险是"两周后空且看起来正常"**：卡池 54 张，按每天新增 5 张算约 **10–11 天**过完，之后 `dueCount` 长期为 0 —— 首页那块**看起来一切正常但已经死了**。这比立刻空更危险（团队会以为做完了）。
- **修正后的约束**：**删除"硬性门槛：卡池 ≥70 张才允许启动 2.1"**，改为「**2.1 可与迭代 1 并行，但 1.1/1.2 必须在 10 天内落地**」（按 §1.2 的 ≥100 张目标，10 天产能即可覆盖周转）。
- **对自诊断的修正**：它把"App 首页改成今日素材→到期复习"放在 30 天第 3 项——**顺序方向对**，但它（以及我上一版）都没区分"立刻空"与"到期静默失效"这两种完全不同性质的失效。前者不存在，后者才是要防的。

### 决策 C：Web 与 App 的分工是否需要重划？

**结论：产品定位上"App 是主力"成立；但工程投入上不能"只投 App"，因为端侧迭代速度被构建卡点锁死。**

- **依据**：App 已超前（FSRS/三色标注/TTS/离线都有），但**CLI 签名不可用，装机必须 DevEco 点 Run + 贴日志**——这是"慢循环"。把全部后续迭代押在 App 上，等于把开发速度绑在最慢链条。
- **"App 唯一主力、Web 只做重活"的代价**：
  1. **速度代价**：快速验证（改一版选材策略、试一版卡形态）无法在 Web/脚本上快速迭代，每次都要等真机日志。
  2. **重做代价**：Web 已有 `practice/wrong/favorites/profile/search` 等页面，App 全量对齐需重写。
  3. **机会成本**：Web 工作台已有现成实现（`editor.html` + `/api/relations`），推迟搬进 web 等于闲置已验证资产。
- **替代方案（我推荐）**：**定位上 App 主力，工程上"管道 + Web 做验证，App 做交付"**。即：策略验证在 Web/脚本闭环，成熟后再进 App。**不要为了"App 唯一"而放弃 Web 作为实验台的价值。**

### 决策 D：两个 release blocker 该不该现在处理？"生产可用但账没记"怎么处置？

**结论：`REL-PRODUCTION-DEPLOYMENT` 现在就补证据关闭；`REL-NEWSLETTER-PROVIDER` 应降级/移出当前发布门禁。**

> **✅ 已落地（2026-09-16）**：`REL-PRODUCTION-DEPLOYMENT` 已实测通过并 `closed`（证据 `docs/release-verification-2026-09-16.md`）；`REL-NEWSLETTER-PROVIDER` 已由 `high` 降为 `medium`，`status` 仍 `open`、`closeEvidence` 仍 `null`（不伪造证据）。`pnpm release:check` 现 exit 0，`daily.yml` 的构建与 Pages 部署步骤恢复执行。
>
> 落地时另发现并修复了一处**独立缺陷**：`scripts/smoke-release.mjs` 硬要求首页含 `/read/` 链接，而零选日首页按设计没有 —— 会让 `daily.yml` 最后一步（部署后冒烟）在零选日必红。已改为首页无链接时退回 `/daily/<日期>/` 取链接，并补了三条 fixture 测试。

- **依据**（`docs/release-readiness.json` + `scripts/release-gate.mjs`）：
  - 门禁逻辑：`status==open` 的 high/critical 直接失败；`closed` 但 `closeEvidence` 不完整也失败（`verifiedAt/verifiedBy/evidence` 三字段缺一不可）。
  - `REL-PRODUCTION-DEPLOYMENT`：生产**实测可用**（`www.meirishizheng.cn` / `api.meirishizheng.cn` 在线），`closeCriteria` 是"记录可审计证据"。**这是"账没记"，不是"事没做"** → 正确处置：跑一遍冒烟（`pnpm run test:smoke`）+ 部署记录，回填 `closeEvidence`，关闭。
  - `REL-NEWSLETTER-PROVIDER`：域名/密钥/webhook/退信演练**确实都没有**，是真实缺失。**但它不该用 high 阻塞主干发布**——订阅邮件不在"时政记忆系统"的关键路径上。
- **正确处置（二选一，我推荐前者）**：
  1. **降级为 medium 并注明"本迭代不阻塞"**（门禁的 `blockingSeverities` 只拦 critical/high，降级后即可放行且账目诚实）。
  2. 或拆分为独立的"订阅功能"任务，从本次 release 范围移出，文档记录"暂缓"。
  - **不要**为了过门禁而伪造证据（这违反项目自诊断 §6"可溯源"的信任底线）。

| **Web 端功能全量对齐 App** | **不做** | 违背"App 主力"；Web 只保留工作台/看板等重活 |
| **通用 AI 对话助手 / AI 生成时政 / AI 代写作文** | **确认不做** | 与自诊断 §6 边界一致，且是幻觉高风险区 |
| **`node_modules.wsl.old` 等改名留存目录** | **删除（迭代 0）** | 污染测试结果 |
| **手机端段落结构卡片 / 视觉层字体子集化** | **推迟** | 属"锦上添花"；内核未跑通时做视觉层=继续给空壳抛光 |

### 新增质量门禁规则（独立建议，请写进 `quality.py` / CI）

> **规则**：`picks.json` 产出时，若 `essay` / `exam` / `extra` **三个槽位同时为空 → 必须判 `degraded` 并写入失败原因，不得静默发布。**

- **依据**：当前 `curation.py:432-439` 只在 `picked` 为空时不写文件；而 `picks.schema.json` 只要求 `minItems:1`，所以"只有 1 篇 + 三槽位全空"这种**合法但错误**的文件会被静默写出（§2.5）。
- **这是设计上的强异常信号**：三个槽位在正常情况下每天至少应有料（essay 评论、exam 文件类、extra 兜底）。
- **配套**：把该规则纳入 `content/_reports/` 的 `qualityStatus`，并在 CI 中作为"非成功质量状态"处理——这正是 `AGENTS.md` 第 8 条「内容源失败、条目异常减少或 Schema 校验失败时，流水线必须给出非成功质量状态」的落地。
